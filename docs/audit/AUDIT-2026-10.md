## Critical

### - [x] C1 — Pull request IDOR (cross-repository access)
Fixed: 2026-10-03, tests: tests/test_pull_requests.py
- **Where:** `backend/app/services/pull_request_service.py` (`_load_pr_with_relations`, `get_pull_request`, `update_pull_request`, `merge_pull_request`, `add_comment`, `add_review`, `add_reviewer`, `remove_reviewer`, `update_comment_outdated_flag`); `backend/app/api/v1/pull_requests.py` (all `{pull_request_id}` routes).
- **Problem:** routes authorize against the repository in the URL, then load the PR by `pull_request_id` alone. A user with access to *any* repo can read, comment on, close, or merge PRs of any other repo (including private ones) by putting the foreign PR id in their own repo's URL.
- **Fix:** every PR lookup takes `repository_id` and filters `PullRequest.repository_id == repository_id`; return 404 on mismatch.
- **Test:** user with access to repo A requests repo A's URL with repo B's PR id → 404, for GET, PATCH, close, merge, comments, reviews, reviewers, diff.

### - [x] C2 — Webhook IDOR
Fixed: 2026-10-04, tests: tests/test_webhooks.py
- **Where:** `backend/app/api/v1/webhooks.py` (`update_webhook`, `delete_webhook`, `list_webhook_deliveries`); `backend/app/services/webhook_service.py` (`update_webhook`, `delete_webhook`, `list_deliveries` use `session.get(Webhook, webhook_id)`).
- **Problem:** an admin of repo A can modify, delete, or read deliveries of repo B's webhooks.
- **Fix:** scope by `Webhook.repository_id == repository.id` in the service.
- **Test:** admin of A patches/deletes/lists deliveries of B's webhook → 404, and B's webhook is unchanged.

### - [~] C3 — Webhook SSRF bypasses
Mostly fixed: 2026-10-04, tests: tests/test_webhooks.py — scheme allow-list, update re-check, ipv4-mapped/CGNAT/ULA/link-local/reserved/multicast/unspecified all blocked, non-blocking resolve, redirects disabled. FOLLOW-UP: DNS-rebinding TOCTOU — _check_ssrf resolves then httpx re-resolves at POST; pin the vetted IP for the actual connection.
- **Where:** `backend/app/services/webhook_service.py` (`_check_ssrf`, `update_webhook`).
- **Problems:**
  1. `update_webhook` never re-checks the URL → create with a public URL, then PATCH to `http://169.254.169.254/`.
  2. Blocklist misses IPv4-mapped IPv6 (`::ffff:127.0.0.1` — an IPv6 address never matches an IPv4 network), `0.0.0.0/8`, `100.64.0.0/10`, `fc00::/7`, `fe80::/10`, multicast, reserved.
  3. No scheme check (only `http`/`https` should be allowed).
  4. `socket.getaddrinfo` is blocking inside async code.
- **Fix:** validate on create AND update; unwrap `ip.ipv4_mapped`; reject if `is_private or is_loopback or is_link_local or is_reserved or is_multicast or is_unspecified` (or not `is_global`); require http/https; resolve via `loop.getaddrinfo`.
- **Test:** PATCH to a metadata/loopback/`[::ffff:127.0.0.1]` URL → 422; `file://` and `gopher://` → 422.

### - [x] C4 — Mercurial file-pattern injection
Fixed: 2026-10-04, tests: tests/test_mercurial_read_only.py
- **Where:** `backend/app/mercurial/read_service.py` — `get_blame` (passes the user's `path` straight to `hg annotate`), `_read_file` (`hg cat`), `_load_per_file_diffstats` (`hg diff --stat -- <path>`).
- **Problem:** hg treats file arguments as patterns even after `--`. `path=listfile:/etc/passwd` makes hg read a server file; `set:`/`re:` allow expensive filesets and ReDoS. Repo contents can also contain such names (e.g. a directory literally named `listfile:`).
- **Fix:** always pass `f"path:{normalized_path}"`. In `get_blame`, also require the path to exist in the revision's manifest before invoking hg.
- **Test:** blame with `path=listfile:/etc/passwd`, `set:**`, `re:.*` → 404/422 and hg is never invoked with a non-`path:` pattern.

### - [x] C8 — Push events silently lost after the first SSH push
Fixed: 2026-10-06, tests: tests/test_event_spool.py
- **Where:** `backend/app/mercurial/ssh_gateway.py` (sets `revforge.request_id` to `""` when `REVFORGE_REQUEST_ID` is unset); `backend/app/services/event_spool.py` (`import_to_db`, `read_pending_events`).
- **Problems:**
  1. Empty request_id → idempotency key `file:` for every SSH push → unique-constraint violation from the second push onward.
  2. `read_pending_events` deletes spool files *before* the DB commit, so any failed batch (duplicate key, deleted repo) loses every event in it permanently.
  3. One bad event poisons the whole batch.
- **Fix:** generate a UUID request_id in the SSH gateway when none is set; use the spool file's unique name in the idempotency key; delete files only after a successful commit; skip (and log) events whose repository no longer exists.
- **Test:** two spooled events with an empty request_id both import; a failing commit leaves the files on disk; an event for an unknown repo doesn't block the others.

### - [x] C9 — HTTP gateway buffers whole clones and rate-limits successful requests
Fixed: 2026-10-06, tests: tests/test_transport_credentials.py — response is streamed chunk-by-chunk; the limiter counts only failed auth and returns 429. FOLLOW-UP: WSGIMiddleware still buffers internally (full streaming WSGI bridge, shared with C13) and the limiter keys on REMOTE_ADDR (proxy IP) — add trusted-proxy client-IP + per-IP failure budget.
- **Where:** `backend/app/mercurial/http_gateway.py` (`HgHttpGatewayApplication.__call__`, `_authorize`, `TransportRateLimiter`).
- **Problems:**
  1. `payload = list(result)` loads the entire hg response into memory → large clones exhaust RAM.
  2. The limiter counts every authenticated request, so a normal clone/push (several requests) plus CI pulls hits 30/min and gets `403`.
- **Fix:** return a generator that yields hg chunks and records the access audit event in its `finally`; count only *failed* authentication attempts and return `429`.
- **Test:** many successful token-authenticated requests are never limited; repeated bad tokens get 429; a real `hg clone` of a fixture repo still works.

### - [x] C12 — Read-only / anonymous principals can write history into any empty repository
Fixed: 2026-10-04, tests: tests/test_transport_credentials.py
- **Where:** `backend/app/mercurial/http_gateway.py` (`classify_hg_http_command` L103-112, `__call__` L198 `allow_push=*`, hook list L215-225); `backend/app/mercurial/ssh_gateway.py::MercurialSshGateway.run` (hook list L166-176). Write access is gated only by the `cmd=` classification (HTTP) and by three hooks (`prechangegroup`, `pretxnchangegroup`, `prepushkey`) on both transports. Both gates can be bypassed.
- **Problem (verified against Mercurial 7.2.3 source):**
  1. **Classification is bypassable on HTTP.** `classify_hg_http_command` reads the *first* `cmd` (`parse_qs(...)[0]`), but hgweb's `multidict.__getitem__` dispatches the *last* (`hgweb/request.py:44-46`). So `?cmd=capabilities&cmd=unbundle` is classified READ and executes `unbundle`. Also `cmd=batch` is hard-coded READ, but `wireprotov1server.batch` dispatches any sub-command (incl. `unbundle`/`pushkey`) guarded only by `proto.checkperm`.
  2. **hgweb's own push check is open.** The gateway sets `web.allow_push=*`, and `scmutil.ismember` returns True for `['*']` even when the user is `None` (`hgweb/common.py::checkauthz` L220-222). So hgweb never blocks the push; the hooks are the only real gate.
  3. **SSH has no built-in check at all.** `wireprotoserver.sshv1protocolhandler.checkperm` is `pass` (`wireprotoserver.py:459-460`), so a read-capable key reaching `peer.unbundle(...)` is gated only by the hooks.
  4. **The hooks miss `stream2`/`stream3-exp`.** `handlestreamv2bundle` (`bundle2_part_handlers.py:621`) applies to any repo with `len(repo)==0` via `streamclone.consumev2`, which runs under `repo.lock()` with **no** `repo.transaction()` — so `changegroup`/`pretxn*`/`prepushkey` never fire (and a `pretxnopen` hook would not fire either). Every provisioned repo starts empty (`provisioning_service` runs `hg init` then marks READY), so an attacker can plant full history before the owner's first push. Anonymous HTTP pushes also skip the `changegroup.revforge` spool hook, so no push event/webhook is recorded.
- **Impact:** unauthorized writes to repository history — anonymous internet users on public repos; any read-role user or read-scoped token on private repos they can read. Breaks the core read/write invariant.
- **Fix:** (a) HTTP: set `web.allow-push=*` only when `can_write`, otherwise set `web.deny_push=*` with empty allow — fail closed in hgweb regardless of `cmd` tricks. (b) reject requests with more than one `cmd`, and classify `batch` by its real sub-commands (query + `X-HgArg-*` + httppostargs), or as WRITE if any sub-command needs push. (c) SSH has no hgweb check, so gate write **before** `sshserver(...)` when `not can_write` (reject any non-read wire command), rather than relying on hooks. (d) consider refusing stream bundle parts on push. Note: a `pretxnopen` hook alone does **not** stop stream2.
- **Test (real hg, both transports):** anonymous (public repo), read-role user, and read-scoped token each push a `none-v2;stream=v2` bundle into an empty READY repo → `hg log` stays empty; `?cmd=capabilities&cmd=unbundle` → 400/403; `cmd=batch` with `cmds=unbundle…`/`pushkey…` → denied; a write user's normal `hg push` still succeeds.

### - [~] C13 — Unauthenticated request-body buffering exhausts API memory (all tenants)
Mitigated: 2026-10-04, tests: tests/test_body_limit.py — body-size cap (413 before buffering, default 256 MiB) added via BodySizeLimitMiddleware. FOLLOW-UP: full streaming WSGI bridge + global concurrency/in-flight-bytes cap still needed (per-request memory still bounded only by the cap).
- **Where:** `backend/app/main.py` L37-45 mounts the gateway via `starlette.middleware.wsgi.WSGIMiddleware`, whose `__call__` accumulates `body += message["body"]` until the full body arrives (`starlette/middleware/wsgi.py:98-104`) **before** `_authorize` runs. No size limit exists anywhere. Distinct from C9 (response buffering).
- **Problem:** `POST /hg/x/y?cmd=unbundle` with no credentials buffers the entire body in memory (quadratic `bytes` concatenation) before authentication; a few parallel uploads OOM the shared API process for every tenant. Authorized large-bundle pushes are also fully buffered.
- **Fix:** serve the gateway from a streaming WSGI server (gunicorn/waitress) or a streaming ASGI→WSGI bridge; authorize from headers before reading the body; enforce a max body size (413), stricter for unauthenticated requests. (Note the public-repo amplification: anonymous discovery → 401 → client re-sends the whole bundle, so the body is uploaded and buffered twice. Starlette also deprecated `starlette.middleware.wsgi`.)
- **Test:** unauthenticated POST with `Content-Length` above the cap → 401/413 without reading the body; peak memory stays bounded; `hg push` ~50 MB over HTTP while polling `/health` keeps health latency bounded.

### - [x] C14 — SSRF via the `remote-changegroup` bundle2 part
Fixed: 2026-10-04, tests: tests/test_transport_credentials.py
- **Where:** Mercurial `handleremotechangegroup` (`bundle2_part_handlers.py`) runs `url.open(op.ui, raw_url)` on a client-supplied `url` param **before** `op.gettransaction()`; only http/https schemes are allowed. RevForge installs no filter. Verified by reading the 7.2.3 source; the mercurial reviewer reproduced a server-side `GET` to a local listener via a read-only SSH `unbundle`.
- **Problem:** any **write** user can make the backend/sshd container issue GETs to internal addresses (cloud metadata, postgres-adjacent services); via C12 **read-only/anonymous** callers can too. The remote error body is echoed back as `remote:` output (a response oracle). The part is honored even if never advertised.
- **Fix:** remove the `remote-changegroup`, `stream2` and `stream3-exp` entries from `bundle2.parthandlermapping` in both server processes — a server never legitimately receives these on a push. This is the same handler-removal fix that closes C12(a) for write users, which a `pretxnopen` hook does **not** (write users are allowed to open the transaction, and `url.open` runs before it anyway).
- **Test:** a write user pushes a hand-built bundle20 with a `remote-changegroup` part pointing at a local listener → listener receives nothing; client sees "missing support for remote-changegroup".

### - [x] C15 — PR "merge" performs no Mercurial integration (cosmetic state flip)
Fixed (record-only): 2026-10-06, tests: tests/test_pr_merge_record.py — merge now verifies the source has actually landed in the target DAG before marking MERGED and records the full target node. A real server-side hg merge/commit/push was deliberately NOT implemented (product decision).
- **Where:** `backend/app/api/v1/pull_requests.py::merge_pull_request_route` (L583-596) + `pull_request_service.py::merge_pull_request` (L139-157). Reproduced against real `hg 7.2.4`.
- **Problem:** "merge" runs only `hg identify --rev <source> --id` (a read) then sets `state=MERGED`, `merger_id`, `merged_revision`, `merged_at`. There is **no `hg merge`, commit, bookmark/branch move, bundle, or push** — the repo on disk is byte-for-byte unchanged. After "merging", `hg log`/`clone`/`pull` show the source changes are NOT integrated, the target head does not advance, and source/target remain two independent heads forever. RevForge nonetheless reports the PR `MERGED` with a `merged_revision`, so product metadata asserts an integration that never happened (worse than a no-op — it desyncs metadata from Mercurial truth). No mergeability/ancestry/conflict check exists either (source-is-already-ancestor and unrelated-histories are both silently "merged"). No audit event is recorded (also violates invariant 7). The test suite never exercises a real merge (fixtures use nonexistent nodes `abc123`/`def456`).
- **Fix:** decide the model. Either (a) implement a real hg-native merge — in a scratch working copy / `hg share` under the native `wlock`/transaction: `hg update <target>` → `hg merge <source>` → abort+surface conflicts on unresolved files → `hg commit` → push into canonical, then async post-push work + audit; or (b) honest **record-only**: require the client to have already pushed the merge and verify server-side that `source` is now an ancestor of the target branch head before accepting `MERGED`, storing the real merge node. Today's code is neither.
- **Test (real hg):** repo with two divergent heads → POST `/merge` → assert `hg heads` still shows both heads and the repo is unchanged (today this "passes" with the repo untouched — the test should flag that); for the chosen design, assert it either integrates or refuses with a clear error.

### - [x] C16 — Merge/review integrity controls are absent (self-merge, ignored CHANGES_REQUESTED, approval inflation)
Fixed: 2026-10-04, tests: tests/test_pr_review_gating.py; migration 0007_pr_review_unique. NOTE: a write-user can still remove a required reviewer and merge with zero required reviewers (governance design), and PR actions remain unaudited (I33) — both tracked separately.
- **Where:** `pull_request_service.py::merge_pull_request` (only guard is `state == OPEN`), `::add_review` (L267-290), `_serialize_pr` approval count (`pull_requests.py:140`).
- **Problem:** merge consults **no** review state — not required reviewers (`PullRequestReviewer.required` is purely informational), not outstanding `CHANGES_REQUESTED`, not any approval threshold, and not `merger != author`. A write-user (today, due to C6, an admin) can create an OPEN PR and immediately merge it with zero review, and CHANGES_REQUESTED reviews are silently ignored. `add_review` has no author-exclusion (author can APPROVE own PR) and **no dedupe / no unique constraint** on `(pull_request_id, reviewer_id)`, so one reviewer can POST `approved` N times and inflate `approval_count` arbitrarily (misrepresents review state now, and is a direct bypass the moment a threshold is added). The review workflow — the platform's core integrity control for private multi-org code — is fully optional.
- **Fix:** a single testable merge-gate policy: no unresolved CHANGES_REQUESTED, all `required=True` reviewers APPROVED, configurable min-approvals, and merger/author policy. Unique constraint on `(pull_request_id, reviewer_id)` with latest-decision-wins (or count distinct reviewers); reject APPROVED where `reviewer_id == author_id`.
- **Test:** author self-merge → 409; merge with outstanding CHANGES_REQUESTED / unsatisfied required reviewer → 409; same reviewer approving twice keeps `approval_count==1`; author review rejected; merge succeeds only once the gate is satisfied.
